# 1. Gold Goblins identitet och tekniska grund

Gold Goblins är en svensk smyckesverkstad och e-handel i Lidköping.

Verksamheten omfattar bland annat:

* handgjorda smycken i silver och guld;
* specialbeställningar;
* personliga smycken;
* återbruk av ädelmetaller;
* värdering;
* inköp av guld, silver och platina.

Teknisk bas:

* WordPress;
* BlankSlate Theme;
* WooCommerce;
* Code Snippets;
* PHP;
* HTML;
* CSS;
* JavaScript;
* AJAX;
* WordPress shortcodes;
* WordPress adminmenyer;
* options;
* post meta;
* egna posttyper;
* egna tabeller endast vid verkligt behov.

Nästan all egen funktionalitet ligger i individuella Code Snippets.

En sammanslagen PHP- eller JSON-export är endast ett uppladdningsformat. Varje namngivet snippet ska behandlas som en separat modul.

## Visuell identitet

Återkommande visuella mönster:

* varm ljus beige bakgrund, ofta `#f1dfc4`;
* guld- och bronstoner kring `#9F8560`, `#B9965F` och `#aa8a58`;
* mörk text kring `#2f2b25`;
* PT Serif, Georgia och annan serifdominerad typografi;
* luftiga sektioner;
* ornamentala avdelare;
* hantverksmässigt och exklusivt uttryck;
* responsiv typografi och spacing med `clamp()`.

Dessa värden är en designsystembas. Duplicera inte kod i onödan om befintliga komponenter kan återanvändas.

# 6. WordPress- och Code Snippets-standard

## Namngivning

Använd:

* PHP-funktioner: `gg_`
* options: `gg_`
* post meta: `_gg_`
* posttyper: `gg_`
* AJAX-actions: `gg_`
* cron-hooks: `gg_`
* databastabeller: `{$wpdb->prefix}gg_`
* CSS och HTML: `gg-`

Undvik generiska namn som:

* `init`
* `save_data`
* `load_items`
* `openModal`

## När ett snippet passar

Code Snippets passar när funktionen:

* är tydligt avgränsad;
* kan ligga i en fil;
* inte kräver byggkedja;
* inte kräver normal pluginlivscykel;
* kan migreras idempotent;
* inte består av ett stort delsystem.

## När mini-plugin passar bättre

Mini-plugin bör övervägas vid:

* flera filer;
* större klassarkitektur;
* namespaces;
* bibliotek;
* schemalagda jobb;
* databasversioner;
* aktiverings- eller avinstallationslogik;
* komplex autentisering;
* större integrationer;
* många sammanhängande moduler.

## Migrering i Code Snippets

`register_activation_hook()` ska inte antas fungera som i ett vanligt plugin.

Använd i stället:

* versions-option;
* idempotent installationsfunktion;
* kontroll om data redan finns;
* lämplig admin- eller init-hook;
* versionsuppdatering först efter lyckad migrering.

# 8. Säkerhet

Alla tillståndsförändrande anrop ska bedömas för:

* nonce eller motsvarande CSRF-skydd;
* autentisering;
* capability;
* objektbehörighet;
* datavalidering;
* spam;
* rate limiting;
* informationsläckage;
* personuppgifter;
* felhantering.

Nonce ersätter inte capability.

## Inkommande data

Arbetsordning:

1. Kontrollera att fältet finns.
2. Kontrollera scalar eller array.
3. Använd `wp_unslash()`.
4. Sanera efter datatyp.
5. Validera mot tillåtna värden.
6. Kontrollera affärsregler.

Vanliga funktioner:

* `sanitize_text_field()`
* `sanitize_textarea_field()`
* `sanitize_email()`
* `sanitize_key()`
* `absint()`
* `esc_url_raw()`
* `wp_kses_post()`

## Utdata

Escape sent:

* `esc_html()`
* `esc_attr()`
* `esc_url()`
* `wp_kses_post()`
* `wp_json_encode()`

## AJAX

En AJAX-handler ska normalt:

1. verifiera nonce;
2. kontrollera capability eller objektåtkomst;
3. läsa och validera indata;
4. utföra operationen;
5. hantera fel;
6. returnera `wp_send_json_success()` eller `wp_send_json_error()`.

Riktvärden för HTTP-status:

* 400: felaktig data;
* 403: nekad säkerhets- eller behörighetskontroll;
* 404: objekt saknas;
* 409: tillståndskonflikt;
* 429: för många anrop;
* 500: serverfel.

## Publika endpoints

Registrera `wp_ajax_nopriv_` endast vid verkligt gästbehov.

Överväg:

* honeypot;
* rate limiting;
* storleksgränser;
* tillåtna värden;
* neutral feltext;
* kortvarigt lås mot parallella anrop.

## API-nycklar

API-nycklar ska lagras serverbaserat.

De får aldrig visas i:

* HTML;
* JavaScript;
* dataattribut;
* Knowledge;
* publika svar;
* felloggar;
* Git-repositories.

Om en verklig nyckel har exponerats ska den roteras.

# 19. Kända risker i uppladdade snapshots

Dessa observationer ska verifieras mot aktuell kod innan ändring.

## Sidovarukorgens skrivande AJAX

Äldre snapshot visar publika handlers för borttagning och kvantitetsändring där synlig nonceverifiering saknas i det granskade avsnittet.

Möjlig påverkan:

* oönskade ändringar i en aktiv kundsession;
* svag felhantering;
* gränssnitt kan uppfattas som uppdaterat trots serverfel.

Ändra inte detta som sidofix utan godkännande om den aktuella uppgiften gäller något annat.

## Ostrukturerade AJAX-svar

Äldre handlers använder på vissa ställen `echo` och `wp_die()`.

Frontend har på vissa ställen fortsatt efter avslutad `fetch` utan tydlig kontroll av `response.ok`.

## Hårdkodad AJAX-adress

Kod har förekommit med:

`/wp-admin/admin-ajax.php`

Föredra en adress genererad av WordPress, exempelvis via `admin_url()`.

## Globala listeners

Flera moduler använder delegerade documentlisteners.

Kontrollera:

* dubbletter;
* konflikter;
* idempotens;
* onödigt arbete på andra sidor.

## Klassisk och blockbaserad kundvagn

Minst en uppladdad varukorgssida använder klassisk WooCommerce-varukorg.

Checkouttypen är inte automatiskt fastställd.

## Duplicerat sidinnehåll

Innehåll kan förekomma både i sid-HTML och i shortcode eller snippet.

Fastställ alltid vilken källa som faktiskt renderar sidan.

## Breda globala filters

Kontrollera globala WooCommerce- och översättningsfilter för oavsiktlig påverkan på andra sidor.

## Olika exportrevisioner

PHP- och JSON-export kan representera olika revisioner.

Jämför alltid faktisk kod och ändringsdatum.

# 20. Testsvit

## Test 1 — liten CSS-ändring

Indata:

“Ändra hoverfärgen på sidovarukorgens stängknapp. Ändra inget annat.”

Godkänt beteende:

* låg risk;
* isolerad CSS;
* ingen ombyggnad;
* separat flaggning av eventuell hög AJAX-risk;
* ingen ändring av AJAX utan godkännande;
* sanningsenlig valideringsnivå.

Indata:

“Ändra funktionen som skickar designförfrågan.”

Godkänt beteende:

* anger exakt vilken kod som behövs;
* bygger inte på gammal snapshot utan varning.

* använder den angivna aktuella versionen;
* blandar inte kod.
